# Проверка кода по критериям ТЗ / брифа

Источники: `README.md`, `docs/user_journey.md`, `docs/cashback_api.md` (раздел «Что лучше сделать в первой версии»).

---

## 1. API из README и user_journey

### 1.1 Categories — **выполнено**

- `GET` / `POST` /api/v1/admin/categories  
- `GET` / `PATCH` /api/v1/admin/categories/{category_id}  

**В коде:** все перечисленные маршруты есть в `server.py`, реализация в `api/categories.py`. Дополнительно есть icon, rule, run/pause, archive, audit по категории.

---

### 1.2 Rules — **не выполнено**

- `GET` / `POST` /api/v1/admin/rules  
- `GET` / `PATCH` /api/v1/admin/rules/{rule_id}  

**В коде:** отдельных эндпоинтов для rules нет. Правила создаются только через категорию:  
`POST /api/v1/admin/categories/{category_id}/rule` в `api/categories.py`.  
Таблица `rules` и миграции есть, отдельного CRUD API для правил — нет.

**Степень:** полностью отсутствует заявленный в README набор rules API.

---

### 1.3 Audit — **выполнено частично**

- В README и user_journey: **`GET /api/v1/admin/audit`** — общий журнал аудита.  
- В cashback_api: фильтры (actor, entity_type, entity_id, action, from/to).

**В коде:** реализован только аудит **по категории**:  
`GET /api/v1/admin/categories/{category_id}/audit` в `api/audit.py` (параметр `limit` 1–500).

**Не выполнено:**
- общего эндпоинта `GET /api/v1/admin/audit`;
- фильтров по actor, entity_type, entity_id, action, from/to.

**Степень:** сценарий «история изменений по одной категории» закрыт; общий аудит и фильтрация — нет.

---

### 1.4 offers/run — **выполнено**

- `POST /api/v1/offers/run` — расчёт категорий для клиента.

**В коде:** маршрут зарегистрирован, обработчик в `api/calculate.py`. Требуется JWT пользователя, возвращаются `items` и `already_selected_categories`.

---

### 1.5 Selection — **частично выполнено**

**GET selection**

- README / user_journey: **`GET /api/v1/client/selection/{selection_id}`** — получение выбора по id.

**В коде:** такого маршрута нет. Есть только `POST /api/v1/client/selection` (подтверждение выбора по телу и JWT).

**Степень:** не выполнено — клиент не может получить детали выбора по `selection_id`.

---

**POST selection (подтверждение)**

- README: **`GET` / `POST` /api/v1/client/selection/{selection_id}**, при подтверждении — заголовок **`Idempotency-Key`**.
- user_journey: подтверждение с `Idempotency-Key`.

**В коде:**
- Маршрут: `POST /api/v1/client/selection` — без `{selection_id}` в пути (другой контракт: выбор задаётся телом `category_ids`, пользователь — из JWT).
- Заголовок **Idempotency-Key** не читается и не используется; в `api/selection.py` и `functions/selection.py` обработки идемпотентности по ключу нет. В БД колонка `idempotency_key` в `selections` есть (в т.ч. в миграциях), но API её не заполняет.

**Степень:**  
- Формат эндпоинта отличается от ТЗ (нет selection_id в URL).  
- Критерий «Idempotency-Key при подтверждении выбора» — не выполнен.

---

## 2. Гарантии сервера (README)

### 2.1 Диапазоны ставок и лимиты — **выполнено**

- В `api/categories.py`: проверки `rate_min`/`rate_max` (в т.ч. `rate_min <= rate_max`), ограничения полей.  
- Лимиты пагинации (offset/limit) на списках.

### 2.2 Идемпотентность и защита от повторных действий — **не выполнено**

- Явно требуется: **Idempotency-Key при подтверждении выбора**.  
- В коде: не реализовано (см. п. 1.5).

### 2.3 Проверка бюджетных инвариантов на сервере — **частично**

- В категориях проверяется `budget_amount >= 0`, валидация полей.  
- Нет отдельного контура: резерв при подтверждении выбора, списание, ledger, проверки вида `reserved + spent <= budget`.  
- В user_journey и cashback_api это отнесено к «что ещё не доведено» (резервирование/списание в транзакции, движок budget control).

## A. Цели ТЗ — что сделано и на сколько

| Цель ТЗ | Реализовано | Комментарий |
|--------|-------------|--------------|
| Управляет категориями через админку | **Да** | GET/POST/PATCH категорий, icon, rule, run/pause/archive, статус, настройки выбора (settings). Аудит по категории. |
| Строит персональные предложения | **Да** | POST /offers/run с JWT, вызов ML, ответ: items, already_selected_categories. |
| Гарантирует соблюдение бюджетов | **Частично** | На сервере: budget_amount ≥ 0, rate_min ≤ rate_max, лимиты. Нет контура резерва/списания при выборе, нет проверки «reserved + spent ≤ budget». |
| Расширяемые механики взаимодействия | **Частично** | Настраиваемый max_selection_count, конфиг all_categories. Нет progress, миссий, слотов в API. |

## E. Критерии оценки Backend — баллы и проценты

Оценки даны по текущему коду. 0% = критерий не выполнен, 50% = частично/для основного сценария, 100% = выполнено последовательно.

---

### 1. Архитектура системы (15 б.)

**Критерий:** Общая структура системы логична; выбор стека, разбиение на компоненты и взаимодействие обоснованы; решение легко объяснить и проследить на всём маршруте.

| Уровень | Описание |
|---------|----------|
| 0% | Структура не прослеживается, компоненты взаимодействуют хаотично. |
| **50%** | **Архитектурные решения понятны для основных компонентов и их взаимодействия.** |
| 100% | Архитектура последовательна и обоснована требованиями кейса на всём маршруте. |

**Оценка: ~50–75%.**  
Стек (aiohttp, asyncpg, разделение api / functions / database) обоснован, маршрут от HTTP до БД прослеживается. Не хватает: отдельного Rules API, общего Audit, Progress в роутере — из-за этого «весь маршрут» по ТЗ не замкнут.

---

### 2. Архитектура сервиса (15 б.)

**Критерий:** Код структурирован: разделение на слои, нет God-объектов и бизнес-логики в контроллерах; зависимости управляемы; сервис расширяем без переписывания.

| Уровень | Описание |
|---------|----------|
| 0% | Границы ответственности смешаны, логика расползается. |
| 50% | Основные зоны ответственности и слои различимы. |
| **100%** | **Структура последовательно выдержана в ключевых частях.** |

**Оценка: ~75–100%.**  
Слои: api (handlers + валидация), functions (бизнес-логика), database (инициализация, миграции). Контроллеры тонкие, вызовы уходят в functions. Зависимости явные (импорты, без глобального состояния).

---

### 3. Модель данных и переходы состояний (15 б.)

**Критерий:** Схема отражает предметную область; переходы состояний явны и защищены от невалидных переходов; нет противоречивых данных.

| Уровень | Описание |
|---------|----------|
| 0% | Схема и переходы выглядят случайными или противоречивыми. |
| **50%** | **Модель поддерживает основной сценарий, ключевые переходы понятны.** |
| 100% | Данные и переходы согласованы и предсказуемы в критических точках. |

**Оценка: ~50–75%.**  
Схема в init.sql: rules, categories (status CHECK running/paused/archived), selections, audit_log, admin_users. CHECK на бюджет и ставки. Переходы статуса категории (run/pause/archive) явные. Минусы: idempotency_key не используется; нет таблицы/полей под резерв и списание бюджета; выбор хранится как несколько строк selections на user без единого «selection_id» для клиента.

---

### 4. Тестирование — проверка бизнес-логики и контрактов (10 б.)

**Критерий:** Есть тесты на ключевую бизнес-логику и API-контракты; успешные сценарии, ошибки валидации и граничные случаи.

| Уровень | Описание |
|---------|----------|
| 0% | Проверяется только успешный ответ. |
| **50%** | **Проверки бизнес-логики и ключевых договорённостей по данным и ответам.** |
| 100% | Критические правила и контракты проверяются последовательно. |

**Оценка: ~50–75%.**  
Есть unit (categories, users, admin) и integration (categories_api, client_api, users_api, admin_auth, audit, calculate_api). Проверяются статусы, коды ошибок (401, 404, 422), валидация (пустое имя, rate_min > rate_max, неверное число категорий). Контракты ответов (поля, типы) частично проверяются; идемпотентность и бюджетный контур не покрыты.

---

### 5. Тестирование — безопасное добавление изменений (10 б.)

**Критерий:** Новый код не ломает существующие сценарии; в конце важнее сохранить работоспособность, чем наращивать объём.

| Уровень | Описание |
|---------|----------|
| 0% | Изменения вносятся без учёта уже собранного сценария. |
| **50%** | **Проверяется, что изменения не ломают работающий сценарий и ключевые переходы.** |
| 100% | Осознанно удерживается сценарий при каждом изменении. |

**Оценка: ~50%.**  
Тесты есть и при изменениях их запускают, но зависимость от фикстур (aiohttp_client, app) и от конфига БД/окружения создаёт риски: при откате conftest интеграционные тесты массово падали. Нет явного описанного «золотого» E2E-сценария и его приоритета при регрессии.

---

### 6. Эксплуатация — выпуск изменений и миграции (5 б.)

**Критерий:** Миграции без потери данных; путь от изменения к запуску понятен; порядок применения прозрачен; откат не магический.

| Уровень | Описание |
|---------|----------|
| 0% | Путь от изменения к запуску неясен, схема меняется неуправляемо. |
| **50%** | **Можно объяснить, как выпускать изменения и обновлять схему без разрушения сценария.** |
| 100% | Выпуск и миграции организованы предсказуемо и безопасно. |

**Оценка: ~50%.**  
Схема задаётся в postgres/init.sql; на старте вызываются ensure_* (ADD COLUMN IF NOT EXISTS, ensure_users_from_csv, ensure_categories_from_csv). Это даёт повторяемый подъём и мягкое добавление полей. Нет версионированных миграций (нумерация, откат), порядок ensure_* зашит в startup() и не описан отдельным runbook.

---

### 7. Эксплуатация — наблюдаемость и диагностика (5 б.)

**Критерий:** Логирование ключевых событий и ошибок; по логам/метрикам/трассировке можно понять, что происходит без отладчика.

| Уровень | Описание |
|---------|----------|
| 0% | Состояние сервиса и сбои локализовать почти невозможно. |
| **50%** | **Есть базовые способы понять, что сервис работает, деградирует или сломан.** |
| 100% | Сигналы позволяют быстро заметить проблему и локализовать её. |

**Оценка: ~50–75%.**  
request_logging_middleware логирует метод, путь, IP, статус ответа; в обработчиках используется logger.exception при ошибках; в ответах об ошибках есть traceId и timestamp. Нет метрик (счётчики, гистограммы) и распределённой трассировки.

### 8. Системная интеграция — API и контракты (15 б.)

**Критерий:** API спроектировано логично; эндпоинты предсказуемы; форматы запросов/ответов консистентны; статус-коды корректны; контракты задокументированы или очевидны из кода.

| Уровень | Описание |
|---------|----------|
| 0% | Точки входа и поведение хаотичны. |
| **50%** | **API и контракты понятны для основного сценария, ответы и ошибки предсказуемы.** |
| 100% | Контракты последовательны и не создают неоднозначности в основных и пограничных сценариях. |

**Оценка: ~50–75%.**  
Единый префикс /api/v1, разделение admin/client, коды 200/201/400/401/404/422/500, единый формат ошибок (code, message, traceId, path, fieldErrors). Swagger описан. Минусы: нет Idempotency-Key в контракте selection; общий audit и progress не представлены в API; часть README не совпадает с фактическими маршрутами.

### 9. Осознанность — архитектурные компромиссы и ограничения (10 б.)

**Критерий:** Команда может объяснить структуру сервиса, БД, синхронность/асинхронность и известные ограничения.

| Уровень | Описание |
|---------|----------|
| 0% | Решения выглядят случайными или заимствованными без связи с кейсом. |
| 50% | Понимаются основные ограничения и компромиссы. |
| **100%** | **Убедительное объяснение выбора структуры, данных и контрактов через требования кейса и слабые места.** |

**Оценка: ~50–75%.**  
В коде и в docs (README, criteria_review, api_testing) видно обоснование: async под I/O, Postgres под целостность, слои под расширяемость. Известные ограничения (нет полного бюджетного контура, нет Idempotency-Key, нет GET selection/progress) зафиксированы в criteria_review. Для 100% не хватает явного краткого «архитектурного решения» с перечислением компромиссов и плана по слабым местам.

## G. Что сильнее всего тянет вниз

1. **Нет Idempotency-Key** при подтверждении выбора — явно требуется ТЗ и критерием «гарантии сервера».  
2. **Нет полного бюджетного контура** — резерв/списание при выборе не реализованы; инварианты «на сервере» выполнены только на уровне полей.  
3. **Rules API и Progress не представлены в API** — в ТЗ перечислены rules, progress, audit; общий audit и GET selection/current отсутствуют.  
4. **Миграции и регрессия** — нет версионированных миграций и зафиксированного приоритета «не сломать E2E» при изменениях.

Усиление по этим пунктам даёт наибольший прирост по критериям и по соответствию ТЗ.
