# Backend сервиса T-Cash

**О проекте.** Backend решает задачу управляемого кэшбэка: админка настраивает категории, правила отбора и бюджеты; клиент получает персональный список категорий (`offers/run`), выбирает их и подтверждает выбор; сервер гарантирует лимиты, идемпотентность и проверку бюджетов на своей стороне.

**Документация API:** после запуска сервера доступны [Swagger UI](http://localhost:8080/docs) и [OpenAPI (JSON)](http://localhost:8080/docs/swagger.json).

## Какую задачу решает backend

Кэшбэк увеличивает оборот и вовлечение, но легко выходит из-под контроля по стоимости. Backend обеспечивает продукт, в котором клиенту интересно, а экономика управляема.

**Основные возможности:**

- управление категориями кэшбэка через админку (создание, правки, бюджеты, диапазоны ставок, правила отбора по возрасту/полу/доходу);
- персональный расчёт предложений для клиента (`POST /api/v1/offers/run`) с учётом правил и при необходимости внешнего ML-сервиса;
- подтверждение выбора категорий с идемпотентностью (`Idempotency-Key`), прогресс клиента, аудит изменений.

**Гарантии:** проверка диапазонов ставок и бюджетов на сервере; защита от повторных действий по ключу идемпотентности; все бюджетные инварианты проверяются в бекенде, а не только в интерфейсе.

## Архитектура системы

Сервис построен по слоёной архитектуре: зависимости направлены внутрь (HTTP → бизнес-логика → данные), что упрощает изменения и расширения.

**Взаимодействие компонентов:**

- **Клиент / Админка** → HTTP-запросы к **aiohttp-приложению** (`server.py`, маршруты в `api/`).
- **Обработчики API** (`api/*.py`) валидируют вход, вызывают **функции бизнес-логики** (`functions/`) и формируют ответ.
- **Бизнес-логика** (категории, правила, выбор, расчёт офферов) обращается к **слою данных** (`database/`) и при расчёте офферов — к **внешнему ML-сервису** (переменная `ML_SERVICE_URL`, по умолчанию `http://127.0.0.1:8008`).
- **Слой данных** (`database/database.py`, `database/functions.py`) выполняет запросы к **PostgreSQL**; миграции схемы — **Alembic** (`alembic/`).

**Основные компоненты:**

| Слой | Назначение | Компоненты |
|------|------------|------------|
| **HTTP/API** | Приём запросов, валидация, ответы, контракты | `server.py`, `api/*.py`, `docs/schemas.py` |
| **Бизнес-логика** | Правила домена, расчёт офферов, бюджеты, идемпотентность | `functions/categories.py`, `functions/selection.py`, `functions/calculate.py` и др. |
| **Данные** | Подключение к БД, транзакции, миграции, загрузка CSV | `database/database.py`, `database/functions.py`, `alembic/` |

**Стек:** Python 3.12, aiohttp, asyncpg (PostgreSQL), marshmallow + aiohttp-apispec (Swagger), Alembic, Docker/docker compose.

**Структура проекта:**

## Модель данных

**Ключевые сущности:**

- **rules** — правила отбора (min_age, max_age, gender, income). Связь: категория ссылается на правило через `rule_id`.
- **categories** — категории кэшбэка: name, subtitle, icon_url, budget_amount, rate_min, rate_max, status, rule_id. Одна категория — одно правило.
- **selections** — выбор пользователя: user_id, category_id, selection_id, idempotency_key. Один пользователь может выбрать несколько категорий (уникальность по паре user_id + category_id).
- **audit_log** — журнал событий по сущностям (entity_type, entity_id, action, actor, details).
- **users** — клиенты (для offers/run и client/selection); **admin_users** — администраторы; **wordly_words** — слова игры T-Word.

**Схема БД:** сущностно-реляционная диаграмма — [ER.png](ER.png) в корне репозитория. Таблицы и связи описаны в миграциях Alembic (`alembic/versions/`).

![ER-диаграмма схемы БД сервиса T-Cash](./ER.png)

**Колонки основных таблиц (кратко):**

| Таблица | Ключевые колонки |
|---------|-------------------|
| **rules** | rule_id (UUID), min_age, max_age, gender, income, created_at, updated_at |

## Переходы состояний

**Категория (status):**

- **running** — участвует в расчёте и выдаётся клиенту. Переход: `POST .../categories/{id}/run`.
- **paused** — временно исключена из расчёта. Переход: `POST .../categories/{id}/pause`.
- **archived** — мягкое удаление, в расчётах не участвует. Переход: `DELETE .../categories/{id}/archive`.

Переходы между running ↔ paused, а также в archived заданы эндпоинтами и логикой в `api/categories.py` и `functions/categories.py`.

**Выбор клиента (selections):**

- Создание записи при подтверждении выбора (`POST /api/v1/client/selection` с `Idempotency-Key`). Повторный запрос с тем же ключом и тем же телом возвращает сохранённый результат (идемпотентность); при том же ключе и другом теле — 409.

Жизненный цикл выбора и сценарии отмены/изменения заданы в `api/selection.py` и `functions/selection.py`.

## Основной сценарий работы

Сценарий, по которому проверяется работоспособность системы:

1. **Настройка** — в админке создаются/редактируются категории, правила отбора и бюджеты (эндпоинты `admin/categories`, `.../rule`, run/pause/archive).
2. **Персональный расчёт** — клиент с JWT вызывает `POST /api/v1/offers/run` и получает список категорий для выбора.
3. **Выбор** — клиент выбирает категории в интерфейсе и отправляет подтверждение: `POST /api/v1/client/selection` с заголовком `Idempotency-Key`.
4. **Прогресс** — `GET /api/v1/client/progress` показывает прогресс по офферам и подтверждённым выборам.
5. **Изменение бюджетов** — админ меняет категории; повторный расчёт и выбор проверяют корректную адаптацию.

Бюджетные инварианты и лимиты проверяются на сервере на каждом шаге.

## Контекст и цель

**Проблема.** Кэшбэк увеличивает оборот и вовлечение, но при этом легко выходит из-под контроля по стоимости. Нужен продукт, в котором клиенту интересно, а экономика устойчива.

**В промышленной постановке** это не разовый «экран выбора категорий»: правила, категории и бюджеты меняются регулярно, а механика остаётся прозрачной и управляемой для бизнеса.

**Цель сервиса:**

- управлять категориями через админку;
- строить персональные предложения (offers/run);
- гарантировать соблюдение бюджетов;
- поддерживать расширяемые механики взаимодействия.

**Баланс:** клиент видит ощутимую и честную выгоду, банк сохраняет контроль бюджета и предсказуемость экономики.

## Бизнес-ограничения и модель категории

**Категория** — управляемая сущность:

- имя, подзаголовок, иконка (`icon_url`);
- бюджет (`budget_amount`), диапазон ставки (`rate_min`, `rate_max`);
- правило отбора (привязка к `rule_id`: возраст, пол, доход);
- статус (running / paused и т.д.), история изменений (аудит по категории).

**Бюджеты — ключевой инвариант:**

- нельзя превышать бюджет категории и общий бюджет (если введён);
- при исчерпании бюджета предусмотрен явный резервный сценарий (например, информирование клиента о недоступности);
- механизм контроля бюджета формален и проверяется на сервере.

**Персонализация** учитывает поведение и стоимость кэшбэка; ML может использоваться для персонализации предложения и оценки ожидаемой стоимости (см. раздел API и модуль расчёта).

---

## Проверяемый E2E-маршрут

1. **Настройка категорий, правил и бюджетов** — админка: создание/редактирование категорий, настройка правил отбора, задание бюджетов и диапазонов ставок.
2. **Запуск персонального расчёта** — `POST /api/v1/offers/run`: получение персонального списка категорий для клиента.
3. **Клиент взаимодействует с механикой** — выбор категорий в интерфейсе.
4. **Подтверждение выбора и повторный вход** — `POST /api/v1/client/selection` с заголовком `Idempotency-Key` для идемпотентности.
5. **Демонстрация прогресса/начислений** — `GET /api/v1/client/progress`.
6. **Изменение бюджетов** — проверка корректной адаптации (обновление категорий через админку, повторный расчёт и выбор).

Весь маршрут должен проходиться целиком; бюджетные инварианты проверяются на сервере.

## API бекенда

Группы эндпоинтов по ТЗ: **categories**, **rules**, **offers/run**, **selection**, **progress**, **audit**.

**Админка категорий и правил**

- `GET /api/v1/admin/categories` — список категорий.
- `POST /api/v1/admin/categories` — создание категории (поддерживается `Idempotency-Key`).
- `GET /api/v1/admin/categories/{category_id}` — категория по ID.
- `PATCH /api/v1/admin/categories/{category_id}` — обновление (имя, подзаголовок, иконка, бюджет, rate_min/rate_max, правило).
- `POST /api/v1/admin/categories/{category_id}/rule` — создание правила для категории.
- `PATCH /api/v1/admin/categories/{category_id}/rule` — обновление/удаление правила (в т.ч. `rule: {}` для сброса).
- `POST .../run`, `.../pause`, `DELETE .../archive` — управление статусом категории.
- `GET /api/v1/admin/categories/{category_id}/audit` — история изменений по категории.
- `GET/POST /api/v1/admin/categories/settings` — настройки механики выбора (лимиты и т.п.).

**Клиентские эндпоинты**

- `POST /api/v1/offers/run` — персональный расчёт предложений (список категорий для клиента).
- `POST /api/v1/client/selection` — подтверждение выбора категорий; обязателен заголовок `Idempotency-Key` для защиты от повторных действий.
- `GET /api/v1/client/progress` — прогресс клиента по офферам и подтверждённым выборам.

**Аудит**

- Аудит по категории: `GET /api/v1/admin/categories/{category_id}/audit`. Ключевые события (создание/изменение категории, смена бюджета, правил) логируются с привязкой к инициатору.

Схемы запросов и ответов описаны в `docs/schemas.py` и доступны в Swagger UI (`/docs`).

## Гарантии сервера

- **Диапазоны ставок:** при создании и обновлении категории проверяются `rate_min`, `rate_max` и их согласованность (в т.ч. ограничения в БД).
- **Лимиты и бюджет:** бюджет категории и валидация задаются на сервере; проверки не дублируются только на интерфейсе.
- **Идемпотентность:** подтверждение выбора (`client/selection`) и при необходимости создание категории поддерживают заголовок `Idempotency-Key`; повторный запрос с тем же ключом и тем же телом не создаёт дубликатов и возвращает сохранённый результат.
- **Защита от повторных действий:** идемпотентность по ключу; при конфликте ключа с другим payload возвращается 409.

Все бюджетные инварианты проверяются на сервере.

## Архитектура и стек

Сервис построен по слоёной архитектуре: слой HTTP/API отделён от бизнес-логики и доступа к данным. Взаимодействие между слоями одностороннее — зависимости направлены внутрь, что обеспечивает предсказуемость изменений и возможность расширения функциональности без переработки ядра.

**Архитектурные принципы**

- **Разделение ответственности:** точка входа (`server.py`) регистрирует маршруты, подключает CORS и middleware валидации; обработчики в `api/` выполняют разбор запроса, вызов функций бизнес-логики и формирование ответа. Правила домена (бюджеты, ставки, идемпотентность) сосредоточены в `functions/`.
- **Единый контур данных:** все операции с категориями, правилами, выборами и аудитом проходят через слой данных (`database/`); миграции схемы выполняются через Alembic с явным порядком применения и отката.
- **Контракты API:** форматы запросов и ответов описаны в `docs/schemas.py` и отражены в Swagger UI; сервер гарантирует соблюдение контрактов и возврат согласованных кодов ответа.

**Слои системы**

| Слой | Назначение | Основные компоненты |
|------|------------|---------------------|
| **HTTP/API** | Приём запросов, валидация входных данных, формирование ответов и ошибок, документация контрактов | `server.py`, `api/*.py`, `docs/schemas.py` |
| **Бизнес-логика** | Правила домена, расчёт офферов, проверка бюджетов и ставок, идемпотентность выбора и создания категорий | `functions/categories.py`, `functions/selection.py`, `functions/calculate.py` и др. |
| **Данные** | Подключение к БД, транзакции, выполнение запросов, миграции схемы, инициализация (в т.ч. загрузка из CSV) | `database/database.py`, `database/functions.py`, `alembic/` |

**Структура проекта (основное)**

- `api/categories.py` — CRUD категорий, правило (rule), run/pause/archive, аудит по категории.
- `api/selection.py` — подтверждение выбора (`client/selection`), идемпотентность.
- `api/calculate.py` — персональный расчёт (`offers/run`).
- `api/audit.py` — список записей аудита по категории.
- `functions/` — бизнес-логика категорий, правил, выбора, расчёта.
- `database/functions.py` — инициализация БД, загрузка категорий из CSV (при необходимости).
- `docs/schemas.py` — схемы запросов/ответов для Swagger.
- `alembic/` — миграции схемы БД.

**Технологический стек:** Python 3.12, aiohttp (HTTP-сервер), asyncpg (драйвер PostgreSQL), marshmallow и aiohttp-apispec (валидация и Swagger), Alembic (миграции), Docker и docker compose (сборка и запуск окружения).

**Модель данных (кратко):** таблицы `rules` (правила отбора: возраст, пол, доход), `categories` (budget_amount, rate_min, rate_max, rule_id, icon_url, статус), `selections` (выбор пользователя, idempotency_key), `audit_log` (события по сущностям); служебные таблицы идемпотентности; таблицы `users`, `admin_users`, `wordly_words` для идентификации и игрового модуля. Переходы состояний категории (running / paused / archived) и жизненный цикл выбора заданы схемой и логикой в коде.

## Авторизация, тестовые данные, интеграции и ограничения

**Авторизация:**

- **Клиент:** JWT выдаётся через `GET /api/v1/users/{user_id}/auth`. Токен передаётся в заголовке `Authorization: Bearer <token>` для эндпоинтов `offers/run`, `client/selection`, `progress` и др.
- **Админ:** регистрация/вход через `/api/v1/admin/auth/register`, `/api/v1/admin/auth/login`; для эндпоинтов `admin/categories`, `admin/.../rule` и т.д. требуется JWT админа.

**Тестовые данные:**

- При инициализации БД можно загружать категории и пользователей из CSV: `data/categories.csv`, `data/users.csv` (логика в `database/functions.py`). Наличие и момент загрузки зависят от окружения и скриптов инициализации.

**Внешние интеграции:**

- **ML-сервис расчёта офферов:** для персонального списка категорий (когда у пользователя ещё нет выборов) бекенд обращается к внешнему сервису по URL из переменной окружения `ML_SERVICE_URL` (по умолчанию `http://127.0.0.1:8008`). Эндпоинт сервиса: `POST .../predict`. При недоступности сервиса запрос `offers/run` завершается ошибкой 5xx.

**Ограничения и компромиссы:**

- Зависимость `offers/run` от внешнего ML-сервиса: при его падении новый расчёт для пользователей без выборов недоступен; кэш по уже выбранным категориям отдаётся без вызова ML.
- Границы MVP и возможные расширения описаны в разделе [Границы MVP и развитие](#границы-mvp-и-развитие).

## Дополнительные возможности

Помимо ядра кэшбэк-сервиса (категории, правила, офферы, выбор, аудит) в состав бекенда входят следующие модули.

**Авторизация и управление доступом**

- Регистрация и вход администраторов (`/api/v1/admin/auth/register`, `/api/v1/admin/auth/login`), модерация заявок (approve/decline) и проверка прав доступа к админ-операциям.
- Идентификация клиента для клиентских эндпоинтов (offers/run, client/selection) с привязкой операций к пользователю.

**Настройки механики выбора**

- Эндпоинты `GET/POST /api/v1/admin/categories/settings` позволяют задавать лимиты и параметры механики выбора категорий (количество категорий, ограничения по периодам и т.п.) без изменения кода.

**Игровой модуль T-Word**

- Отдельный контур API для словесной игры (старт игры, ввод попытки, получение состояния и статуса пользователя). Реализован в модулях `api/wordly.py` и связанных таблицах БД; не затрагивает логику кэшбэка и может использоваться как дополнительный канал вовлечения в рамках единого приложения.
